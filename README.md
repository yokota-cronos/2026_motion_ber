# モーション × BER 同時計測

OptiTrack（Motive / NatNet）で身体の 7 マーカーを撮りながら、ADP3250 × 2 台の NFC VHBR 上り BER を測る。
画面にはマーカーの 3D 表示と Web カメラの映像も出し、BER の記録中はカメラも録画する。
BER の 1 収録ごと・テストフレーム 1 枚ごとに、そのときの姿勢を対応付けて残す。

モーションからコイルのインピーダンスを 100 ms 先まで先読みして、リーダの W2−W1 位相差を**収録の直前に**
自動で合わせられる（`--phase-model imp_phase_model.py`。「位相の自動調整」の節）。

## 使い方

```bash
uv run motion_ber_gui.py                       # http://127.0.0.1:8766 が開く
uv run motion_ber_gui.py --connect             # 起動と同時に OptiTrack (127.0.0.1) へ繋ぐ
uv run motion_ber_gui.py --group lower         # 下半身
uv run motion_ber_gui.py --fake-motion         # Motive 無し。合成モーションで画面と記録を試す
uv run motion_ber_gui.py --camera 0            # カメラ 0 も開く（画面の「カメラ」欄からも開ける）
uv run motion_ber_gui.py --replay              # 記録の再生専用の画面（いちばん新しい記録。装置には触らない）
uv run motion_ber_gui.py --replay <フォルダ名>  # 記録を指定して再生
uv run motion_ber_gui.py --video-only          # 再生専用の画面を「動画のみ」で開く（--replay <フォルダ名> と併用可）
uv run python tests/test_motion_ber.py         # 装置無しで確かめられる部分のテスト
```

1. Motive を起動して Data Streaming を ON（Labeled Markers を含める。既定は 127.0.0.1・Unicast）。
2. 画面の「モーション」欄で計測部位を選んで「接続」。緑の ● が 7 個そろうのを確かめる。
   カメラも使うなら「カメラ」欄で番号を入れて「接続」（この PC では 1 = 外付けの C920、0 = 内蔵。画面の既定は 1）。
3. あとは `ber_gui.py` と同じ。「開始」で BER の測定と記録が始まる。

- **OptiTrack のフレームが来ていないと「開始」を断る。** BER だけ測りたいときは「OptiTrack なしでも開始できる」を入れる。
- 測定中は計測部位の変更・接続し直し、カメラの繋ぎ直しができない（CSV の列や録画が途中で変わるため）。
- 起動のオプション（`--div`、`--reader`、`--tag`、`--payload`）と装置の注意は `../2026_nfc_vhbr_ber/README.md` と同じ。
  **強制終了しないこと**も同じ（画面の終了ボタンか `POST /api/shutdown`）。
- Motive が別の PC のときは「Motive の IP」と「この PC の IP」を入れる。Multicast なら チェックを入れる。

### 補正の状況（記録中）

モーションの欄のすぐ下に、**収録 1 回ごとの BER と、その収録で使った位相**を同じ時間軸で並べる（`/api/motion` の `corr`、直近 300 回）。

- 上の数字: 直近の収録の BER（良い < 10⁻⁵ ≤ 注意 < 10⁻³ ≤ 悪い）、直近 10 回の BER、この収録の位相差と状態
  （自動補正 / 基準を取っています k/5 / 補正なし）、補正量（初期位相から）、先読み（設定と、最後のモーション → 窓の中央の実測）、
  自動補正した収録の BER と補正なしの収録の BER（表示中の範囲。姿勢が違うので、そのままの比較にはならない）
- 図: 上 = 収録ごとの BER（● 自動補正、○ 補正なし、▽ 誤り 0（上限 3 ÷ ビット数））、下 = その収録の位相差（点線 = 初期位相）。
  灰色の帯 = 基準を取っている間。点にマウスを載せると、その収録の値が出る
- 「3D とカメラを隠す」で、下の BER の図（①〜④）を上に寄せられる（ブラウザに覚える）

### 3D 表示とカメラ

- **3D 表示**: 最新の姿勢を約 30 Hz で描く。ドラッグで回転、ホイールで拡大縮小、ダブルクリックで戻す。上の軸は Motive の設定に合わせて選ぶ（この台は Z が上、既定も Z）。ボーン・配色・肘／膝の角度は `live_dashboard.py` と同じ。見えていないマーカーは赤字で出る。
- **カメラ**: OpenCV（DirectShow）で開き、640 px 幅の MJPEG で画面に流す。「カメラも録画」が入っていれば、BER の記録と同じ期間だけ記録フォルダに録画する（元の大きさのまま）。
- OpenCV が入っていない環境でも BER とモーションは使える（カメラ欄が無効になるだけ）。

### マーカー名の対応

ラベル付きマーカーの `marker_id = i` を、部位ごとの名前リストの `i` 番目に割り当てる（`sync_optitrack_nanovna.py` と同じ規則）。
並びは `motion.py` の `MARKER_GROUPS`。Motive のアセットを変えたら、画面の「受信フレームの構造」で `marker=` を見て合わせる。
上半身と下半身のアセットを同時に配信しているときは `MARKER_MODEL_ID` に `model=` の値を入れる。

## 記録されるもの

`ber_gui.py` の記録フォルダ `~/nfc_vhbr_captures/log/<日時>_<条件>/` に、元の `conditions.json`・`ber_log.csv` と並べて:

| ファイル | 1 行 | 主な列 |
|---|---|---|
| `motion.csv` | Motive の 1 フレーム（全部） | `t`、`wall`、`OptiFrame`、`OptiTime`、`OptiMidExp`、`n_valid`、`<マーカー>_X/Y/Z` [m]（見えていなければ空） |
| `ber_motion.csv` | BER の 1 収録（既定 0.1 秒） | `t_start`/`t_end`、レベル・位相（`phase_src` = manual/auto）、BER、収録窓の `motion_frames`・`valid_frac`（全点見えていた割合）、`<マーカー>_X/Y/Z`（窓の平均）、`<マーカー>_dev`（窓の中で平均から最も離れた距離 [m]）、`raw_file`（この収録の生データ。無ければ空） |
| `cap_*.ad3` | 収録 1 回の生データ（「生データも記録」のときだけ。1 本約 20 MB） | 「記録の再生」で波形を描くのに使う |
| `frames.csv` | テストフレーム 1 枚（600 ビット） | `cap`、`t`、`errors`（−1 = 取得失敗）、`OptiFrame`（いちばん近い Motive フレーム） |
| `camera.mp4` / `camera_frames.csv` | カメラの 1 コマ | `video_frame`（動画の何コマ目か）、`t`（そのコマを受けた時刻）。カメラを繋いでいて「カメラも録画」のときだけ |
| `phase_pred.csv` | 位相の自動調整の 1 回（入れているときだけ） | `cap`（この位相で撮った収録）、`t`、`horizon`、`phase`（指定値）、`sent`、`phase_model`、`base`（初期位相）、`delta`（補正量）、`t_motion`、`t_decided`、`L_Z_R`〜`R_Z_X`（`imp_phase_model.py` のとき） |
| `motion_conditions.json` | — | 部位、マーカー名、カメラの設定、時計の対応（`perf0` ↔ `wall0`） |

`camera.mp4` の再生速度は名目の fps なので、**動画の時刻ではなく `camera_frames.csv` の `t` を使うこと**（カメラの実際のコマ間隔は明るさなどで変わる）。

`t` はどの CSV でも同じ時計（記録開始からの秒）なので、`frames.csv` と `motion.csv` は `t` か `OptiFrame` で結合できる。
学習用には、フレームの誤りを `OptiFrame` で姿勢に結び付けるのが最も細かい。

測定は**断続的**: 95 ms 撮って約 0.5 秒かけて USB で吸い上げる、の繰り返し（周期 約 0.64 秒。下の「収録の流れ」）。
BER があるのは収録窓の中だけで、モーションは全区間ある。

### 収録の流れ

収録窓の既定は **95 ms**（位相の変更 5 ms と合わせて 100 ms。画面の「1 回の収録」に足してある）。1 周はこう回る:

```
収録スレッド:  [予測 ~26 ms] [位相を変える ~10 ms + 待ち 5 ms] [収録窓 95 ms] [USB 転送 ~0.5 s] → 次の周
処理スレッド:                                     （次の収録が始まってから）DDC (~110 ms) → 復調 → 画面・CSV
```

- ADP3250 は本体のメモリに 100 MS/s で撮り、USB で吸い上げ終わるまで次を撮れない。**95 ms を 100 ms ごとに切れ目なく撮ることはできない**
  （95 ms 分 = 約 19 MB の転送が約 0.5 s。並べられるのは PC 側の処理だけ）。
- 処理を別スレッドにしたので、周期は「予測と位相 ~40 ms + 窓 + 転送」で決まる。2026-11-18 の実機で **0.64 s**（それまでは窓 100 ms で約 1.35 s）。
- 処理は**次の収録が始まってから**始める。転送の直後に始めると、次の予測と CPU を取り合って予測が 26 → 49 ms に延び、
  窓の中央まで 122 ms になっていた（2026-11-18 18:27 の記録）。直した後は予測 24 ms・窓の中央まで 89 ms（合成モーション）。
  処理（~0.3 s）は次の収録（窓 + 転送 ~0.6〜0.9 s）の間に終わるので、周期は変わらない。
- カメラの録画や画面を開いていると USB の転送が遅くなる（18:27 の記録では窓 + 転送が 917 ms、周期 0.99 s）。
- 処理が追いつかないときは、収録が 1 本ぶん待つ（キューの長さ 1）。撮った収録は止めるときも全部処理してから閉じる。
- ADP3250 に触るのは収録スレッドだけ。

## 同期のしかた

ADP3250 と Motive は外部トリガで結ばれていない。どちらも PC の `time.perf_counter()` で時刻を打って突き合わせる。

| | 時刻 | 乗っている未較正の遅れ |
|---|---|---|
| 収録窓 | `FDwfAnalogInConfigure` を呼ぶ直前 〜 + 点数 / fs | 開始を USB で伝える遅れ（~1 ms の見込み） |
| テストフレーム | 収録窓の先頭 + 窓の位置 / 受信部の fs | 上と同じ（DDC の遅れ < 1 µs は無視） |
| モーション | NatNet のフレームを受けた時刻 | Motive の処理・配信（数 ms） |

フレーム 1 枚は FC/8 で約 0.4 ms、モーションは 120 fps で 8.3 ms 間隔なので、精度はモーション側で決まる。
ずれをきちんと詰めたいときは、両方に出る物理的な出来事（コイルを急に動かして BER が跳ねる所）で一度較正する。

**装置を繋いだ状態ではまだ動かしていない**（この PC には WaveForms も Motive も無い）。
装置無しのテストで確かめたのは: マーカーの対応付け、NatNet のコールバック、収録窓とモーションの突き合わせ、
3 つの CSV、位相の差し込み口、HTTP の各 API、画面の表示（合成モーション）、カメラの配信と録画（合成カメラと内蔵カメラ）。
初回は `--fake-motion` → Motive だけ → ADP3250 も、の順に確かめること。

## 記録の再生

「記録の再生」欄で記録フォルダ（`~/nfc_vhbr_captures/log/` の中の、`motion.csv` があるもの）を選んで「開く」。
シークバー 1 本で、次が同じ時刻にそろって動く。

| | 何を出すか |
|---|---|
| 3D 表示 | `motion.csv` の、その時刻にいちばん近い姿勢 |
| カメラ | `camera.mp4` の、その時刻までに撮れた最後のコマ（`camera_frames.csv` の時刻で引く） |
| タイムライン | 収録ごとの BER（青 = 生データあり、灰 = なし）。クリックでその時刻へ |
| ①〜③（元の画面） | **生データのある収録の中だけ**、その収録をライブと同じ手順（`fast_ddc` → 受信部の設定 → 窓の位置 → まとめて復調）で復調し、その時刻のテストフレームを描く。**フレームごとの誤り数はライブの `frames.csv` と一致する**（実機の記録で 406/406）。元の「再生」の手順（`ddc()` + 間引き 8 固定）は FC/8 で 1 枚もフレームが取れないので使っていない |

- 操作: 再生／停止、速さ（×0.02〜×2）、「収録の中だけ」（収録と収録の間＝転送待ち約 0.5 秒を飛ばす）、収録単位・テストフレーム単位の送り。
- **波形まで見たいときは、測定のときにライブ欄の「生データも記録」を入れる。** 0.1 秒の収録 1 回で約 20 MB（1 分で約 1.2 GB）。
  どの収録がどの `.ad3` かは `ber_motion.csv` の `raw_file` 列に残る。
- 最初の 1 回だけ 1.4 秒ほどかかる（受信部の立ち上げ）。収録を移るたびに 0.15 秒ほど（収録 1 本の復調）、同じ収録の中では 1 フレーム 30 ms 前後。
- 再生中は BER の測定を始められない（閉じてから）。

### 先読みの答え合わせ（3D 表示の「予測を重ねる」）

**ライブ（記録中）:** 3D 表示の見出しの「予測を重ねる」を入れると、**直近の収録の位相を決めるのに使った予測**だけを重ねる
（収録 1 回に 1 つ。基準を取っている最初の 5 回と、位相を変えなかった回は出さない）。

- 破線のボーンと白抜きの点 = 収録の直前に予測した姿勢（先読みの時間だけ先 = 窓の中央）
- 灰色 = その収録窓（95 ms）の実際の姿勢（平均）。両者を細い線で結ぶ。実線の色つきの骨格は、いまの姿勢（動き続ける）
- 右下に誤差（左右の前腕・肘 [mm]）、予測した姿勢と窓の実際の姿勢から出した位相差、最後のモーション → 窓の中央の時間
- 窓が済んでから出す（次の収録まで約 1 秒、同じ予測を出し続ける）。予測した姿勢はモデルが `_pose` で返し、記録には書かない

**記録の再生:** 「表示」で選ぶ（既定は「両方」）。

- **補正に使った予測**（収録窓の中だけ）: その収録の位相を決めた予測（破線）を、その時刻の実際の姿勢（実線）に重ねる。
  窓の平均の姿勢は描かない。図の下の誤差・位相差も、**その時刻の実際の姿勢**と比べた値（窓の中で再生を進めると変わる）。
  基準を取っていた収録・位相を変えなかった収録には出ない。
  - 2026-11-19 以降の記録は `phase_pred.csv` の `pred_<マーカー>_X/Y/Z`（記録時の予測そのもの）を使う。
  - それより前の記録は、記録時の履歴から**記録時のモデル**（`models/imp_1111_alpha1.joblib`、Ridge を作り直す前の α = 1）で出し直す。
    記録時の位相（`phase_actual`）との差は 18:53・11/12 19:31 の記録で最大 0.04°（同じ予測になっている）。ファイルが無ければ今のモデルで出し直し、
    記録時との差を図の下に出す。2026-11-18 より前の記録は `phase_pred.csv` の `cap` が「直前の収録」なので、`cap + 1` の収録に出す。
- **連続の予測**: その時刻の、先読みの時間だけ前までのモーションから予測した姿勢（下）。
- **両方**: 収録窓の中は補正に使った予測、外は連続の予測。
- 説明（誤差・位相差など）は 3D 表示の下に出す。

**3D 表示の向き:** 動画のカメラと同じ側（本人の正面）から見る（それまでは背中側からで、動画と左右が逆だった）。
記録の再生で `overlay_calib.json`（再生専用の画面で記録を開くと作られる）があれば、その記録のカメラの位置から。
無ければ 11/12・11/18 の較正のカメラの向き（胸から見て yaw 2.99 rad・仰角 0.25 rad）。見出しの「カメラの向き」かダブルクリックでこの向きに戻る。
ドラッグで回して背中側から見ていると（動画と左右が逆）、図の右上に赤字で出る。

**記録の再生（連続の予測）:**

記録を開いて、3D 表示の見出しの「**予測を重ねる**」を入れると、実際の姿勢（実線）に、**先読みの時間だけ前までのモーションから
Ridge で予測した姿勢**（破線のボーンと白抜きの点）を重ねる。同じマーカーどうしは細い線で結ぶ（= 予測の誤差）。

- 計算はライブの位相の自動調整と同じモデル・同じ手順（`imp_phase_model.forecast_series`。過去 8 点を 0.02 s 刻みに補間 → 標準化した Ridge）。
  モデルを作り直したら GUI を起動し直す（読み込んだモデルを覚えているため）。18:53 の記録で、標準化前 → 後に位置 RMSE 10.5 → 8.0 mm、位相 1.62 → 1.18°。
  起点を「各フレームの時刻 − 先読み」にして、記録の全フレームぶんを記録を開いたあと裏で 1 回だけ計算する（2 万フレームで 1 秒弱）。
  ライブで実際に使った予測（`phase_pred.csv`）との差は、2026-11-18 18:53 の記録で位相にして中央値 0.004°。
- 先読みは 50〜300 ms から選べる（既定は記録で使った値）。
- 右下に、その時刻の誤差（左右の前腕と肘 [mm]）、予測した姿勢と実際の姿勢から出した位相差、記録全体の RMSE を出す。
- 収録窓の中だけでなく、モーションがある時刻ならどこでも見られる（Ridge の当たり外れを動きの局面ごとに見る用）。
- 記録中に「マーカーの左右が逆」を入れていた記録は、モデルに渡す名前を同じように入れ替える（`fix_lr.py` で直した記録はラベルどおり）。

④ は BER と回路図（`assets/coil_drive.png`）で、電圧源の横に位相を書く（左 = W1 = 0°、右 = W2 = 位相差）。収録と収録の間は直前の収録の値。

**動画のみ:** 見出しの「動画のみ」（キー `V`）で ①③④ を隠し、録画した動画だけを 16:9 の枠いっぱいに出す
（骨格・頭の上の BER と位相差・背景を薄くする処理はどれも出さない。①③④ の復調もしない）。
もう一度押すと元に戻る。ブラウザに覚える。`--video-only` で起動するか、`?mode=video`（戻すのは `?mode=all`）を付けて開いても選べる。
操作の欄（再生・タイムライン）はそのまま下にある。

**人物だけ（背景を薄く）:** MediaPipe で人物を切り出し、背景を白へ寄せて薄くする（既定で入）。人物の輪郭から外側へ約 10 px（幅の 1.6 %）は元の背景のまま残す（際まで薄くすると服の縁と背景の境目が分からない。`overlay.fade_background` の `margin`）。初めて開いた記録は、
裏で動画の全コマを処理して記録フォルダの `person_mask.npz` に置く（動画モードで追跡するので、腕を伸ばしたコマでも人を見失わない。2 分の動画で約 2 分。進み具合は
右上に出る）。次からは読むだけ。まだ処理していないコマは、出すときにその場で作る。

| 左 | 右 |
|---|---|
| 動画に**実測したマーカーの骨格**を重ねたもの。下に再生の操作とタイムライン | 上: ① リーダ出力と包絡線。上に送ったビット、下に復調したビット（誤りは赤）<br>下: ③ 復調後の IQ と ④ BER の数値（現在・累積・この収録・このフレーム） |

**動画への重ね方:** カメラと OptiTrack は較正していないので、記録そのものから求める（`overlay.py`）。

1. 動画を 150 コマ間引いて MediaPipe Pose で骨格を取る（初回だけ約 10 秒。`pose_mediapipe.npz` に残す）
2. マーカーを MediaPipe の点に対応させる: `R_joint` = 右肘、`R_upperarm` = 肩から肘へ 2 割、`R_forearm` = 肘から手首へ 9 割、
   `chest` = 両肩の中点（下半身は腰・膝・足首で同様）。MediaPipe の点は関節の中心（腕の中）だが、マーカーは腕の
   **外側の表面**に付いているので、手足の点は胴体から離れる向きに「肩幅 × ずらし量」だけずらしてから対応させる。
   ずらし量は記録ごとに誤差が最小になるものを選ぶ（`overlay.py` の `OUTWARDS`）
3. 同じ時刻の「マーカーの 3D 座標」と「動画上の位置」の組から、カメラの位置と向きを `solvePnP` で求める。
   焦点距離は C920 の公称値（640×480 で 500 px）に固定、カメラの遅れ（動画とモーションの時刻のずれ）は探す
4. 以後は各コマの時刻のマーカーをそのカメラで投影して描く（MediaPipe の骨格の代わりに実測の骨格を出す）
5. **動画に写ったマーカー（反射材の白い玉）で詰める。** 投影の近くの、小さく白い丸（明るく彩度の低いもの。服のベージュの線とは
   彩度で分ける）を探して対応にし、カメラ（焦点距離も）を解き直す。MediaPipe からの目安は実際のマーカーと数〜15 px ずれるが、
   これで玉に対して誤差 1 px 前後になる（2026-11-02 の記録: 中央値 0.8 px・90 % 3.6 px）。玉が 60 個未満しか見つからなければ
   MediaPipe の較正のまま。結果は `overlay_calib.json` の `balls`

結果は `overlay_calib.json`。2026-10-27 の 30 秒の記録では、左右を直し外側へのずらし（肩幅 × 0.20 ≈ 7 cm）を入れて**誤差 4.7 px（中央値）**。ずらさないと重ねた骨格が腕の中心を通り、誤差も 6.4 px だった。

- マーカーは体の正面のほぼ 1 枚の面に並ぶので、焦点距離は記録からは決まらない（探すと上限に張り付いた）。だから公称値に固定している。
  同じ理由で「正面から」と「左右を入れ替えて背中から」も見分けにくいので、ラベルどおり（`R_*` = 本人の右）を基本にしている。
- 対応の比（2 割・9 割）は体の寸法からの目安。マーカーの付け方を変えたら `overlay.py` の `MARKER_TO_MP` を直す。
- 「MediaPipe の骨格」を入れると、較正に使った対応点を白い線で重ねて見られる（コマごとに計算するので少し重い）。
- 動きの少ない記録ではカメラの遅れがほとんど決まらない。遅れ 0 より 5 % 以上良いときだけ採る。
- 「較正し直す」で最初からやり直す（`overlay_calib.json` と `pose_mediapipe.npz` を作り直す）。

MediaPipe の姿勢モデル（`models/pose_landmarker_full.task`、約 9 MB）は初回に Google から取ってくる（git には入れない）。
MediaPipe が `opencv-contrib-python` を求めるので、OpenCV はそちらに替えた（`opencv-python` と同じ `cv2`。両方入れると壊れる）。

### Motive のラベルを左右逆に付けて撮ったとき

```bash
uv run fix_lr.py <記録フォルダ名>          # R_* と L_* の名前を入れ替える（数値はそのまま）
uv run fix_lr.py <記録フォルダ名> --flips  # 記録の途中で左右が入れ替わった所を見つけて、その後ろの値を戻す
uv run fix_lr.py <記録フォルダ名> --undo   # 元に戻す（どちらをかけた後でも、いちばん元に戻る）
```

**Motive は記録の途中で左右のラベルを入れ替えることがある。** 2026-10-28 の 11 本を動画と照らすと、7 本が最初から最後まで逆、
4 本が正しく、そのうち 14:31 の 1 本は 43.2 s から逆になっていた。入れ替わった瞬間は右と左のマーカーが互いの位置へ
約 40 cm 飛ぶので、`--flips` は対ごと（上腕・肘・前腕）にそれを見つけ、後ろの値を始めの割り当てに戻す
（`motion.csv` の値と、そこから計算している `ber_motion.csv` の収録窓の平均・動いた量を書き換える）。
始めの割り当て自体が逆なら、続けて `--flips` なしもかける。どちらが必要かは、再生専用の画面で赤（右）の骨格が
本人の右腕に乗っているかで見る。

`motion.csv` と `ber_motion.csv` の列名、`motion_conditions.json` の `marker_names` だけを入れ替え、元のファイルは
`_before_fix_lr/` に残す。`motion_conditions.json` に `lr_fixed`（直した日時）が入る。動画への重ね合わせの較正
（`overlay_calib.json`）は消すので、次に開いたとき作り直される。

2026-10-27 の `…_30s` はこれで直した。直す前は較正の誤差が 8.0 px、直した後は 6.4 px で、カメラの位置も床から約 1.3 m
（三脚の高さ）になった。左右を取り違えたままでも較正は「背中側から見たカメラ」として解けてしまうので、
**誤差の大きさだけでは気づけない**。動画で赤（右）の骨格が本人の右腕に乗っているかを見て確かめる。

## 位相の自動調整

```bash
uv run train_imp_model.py                                   # 最初に 1 回（数分）。models/imp_1125.joblib（470 MB、git には入れない）
uv run train_imp_model.py --dataset 1118                    # 7 マーカーの記録・配信用（models/imp_1118.joblib。あれば自動で使う）
uv run motion_ber_gui.py --phase-model imp_phase_model.py --group upper_side   # 画面の「位相の自動調整」で入れる
uv run motion_ber_gui.py --phase-model imp_phase_model.py --horizon 0.2   # 先読みを 200 ms で始める（既定 0.1。画面でも変えられる）
```

渡したファイルの `predict_phase(motion) -> float | None` を**収録 1 回ごとに 1 回、その収録の直前に**呼び、
返した位相を収録スレッドがそのまま入れて（`set_phase_fast`: 位相を変えて `PHASE_SETTLE_S` = 5 ms 待つ。手で変えたときの
`Bridge.set_phase` は元どおり 50 ms 待つ）、すぐその収録を撮る。続けて叩くとリーダが固まるので、収録 1 回に 1 回より上げない。
`motion` の中身と守ることは `phase_control.py`、モデルの書き方の例は `phase_model_example.py`。
画面の「位相の自動調整」で入り切りする。モデルが例外を出したら自動で切る。

### 補正のゲイン（「補正のゲイン」、`--gain`）

送る位相 = 初期位相 + **ゲイン** ×（モデルの位相 − 基準）。既定 1（モデルのまま）、0〜2。次の収録から効き、基準は取り直さない。
`phase_pred.csv` の `delta` はモデルの補正量のまま（掛ける前）、`gain` が掛けた値、`phase` = `base` + `gain` × `delta`（+ `test_offset`）。
画面の「補正の状況」の補正量は掛けた後（吹き出しに「モデル x° × ゲイン」）。

2026-11-20 14:24 の補正量の試験（タグは左腕側、1118 のモデル）では、打ち消しが最も深くなるのは **ゲイン ≈ 0.6**
（負の補正 = 右腕を上げる向きで 0.62、正の補正で 0.50）。モデルは左右どちらでも補正を約 1.6 倍入れすぎていた。
ExtraTrees の学習データ（1118 の VNA 測定）は今と別のコネクタで測っているので、コネクタでコイルの Z の見え方が変わったぶんが
疑わしい。いまのゲインで合っているかは、ゲインを入れたまま補正量の試験をすれば分かる（どの組でも最小が 0 付近なら合っている）。

### 補正量の試験（「試験: 補正にオフセットを足す」、`--offset-test`）

モデルの補正量そのものが合っているかを、腕を振る動作のまま確かめる。入れると、基準を取り終えた後の収録ごとに
`phase_control.TEST_OFFSETS`（既定 −12・−8・−4・0・+4・+8・+12°）のどれかを自動補正に足す
（7 回で 1 巡、巡ごとに並べ替える。腕振りの周期と揃わないように）。足した値は `phase_pred.csv` の `test_offset`
（`phase` = `base` + `delta` + `test_offset`）、試験だったことは `motion_conditions.json` の `offset_test`。
画面では文字が赤くなり、「補正の状況」の補正量の下と、グラフの吹き出しに「試験 ±x°」が出る。ふだんの測定では切っておく。

```bash
uv run analyze_offset_test.py                  # いちばん新しい試験の記録
uv run analyze_offset_test.py 20261120_1530    # 記録フォルダ名の先頭（複数可。まとめて集計）
```

モデルの補正量の大きさ・向きで収録を分け、オフセットごとに BER と peak（入力の振れ。小さいほど打ち消しが深い）を並べる。
モデルが正しければ最小はオフセット 0。x° にずれていれば、その組の本当に要る補正 ≈ モデルの補正量 + x。
最小が 0 付近なのに peak が「補正量が小さい組」まで下がらなければ、位相だけでは打ち消せていない（振幅の比のずれ）。
1 組・1 オフセットあたり数十回あると頂点が安定する（収録 1 秒に 1 回強なので、片腕ずつ上げる動作で 5〜10 分）。

### モーションからインピーダンスを先読みするモデル（`imp_phase_model.py`）

`../2026_motion_to_meander_imp/report_20261013_dataset1013ver1.pdf` の 4 節と同じ手順（学習データは 1118。
`report_20261111_dataset1111.pdf`・`report_20261118_dataset1118.pdf` の 4 節も同じ手順）:

1. 呼ばれた時点までの直近のモーションから、過去 8 点（0.02 s 間隔）のマーカー位置を取り、**Ridge AR** で h 秒先のマーカー位置を予測する。
   **Ridge に渡すのは chest に対する相対座標**（chest 以外の 6 マーカー − chest、18 次元。2026-11-19 から。それまでは 7 マーカーの絶対座標）。
   前かがみ・腕を大きく上げる・歩くなどで chest そのものが動いても、腕と胸の位置関係だけを予測する。ExtraTrees の特徴量は平行移動で
   変わらないので、相対座標の予測だけでインピーダンスが出る。画面・記録用の予測した姿勢は「いまの chest の位置」に足して出す
   （先読みの 0.1 s の間の chest の動きは入らない）。1111 の評価では絶対座標とほぼ同じ（0.1 s 先 3.07 → 3.05°）。1118 の動きに
   人工的に体の揺れ（全マーカーを一緒に ±5 cm・1 Hz）を足すと、絶対座標は位相の誤差 1.66 → 3.31° に悪化、chest 相対は 1.65° のまま。
   **ただし体の傾き（回転）は消せない**（相対座標は部屋の座標軸のまま。前かがみは平行移動と回転の両方）。
   入力（過去 7 点の変位）と出力は**標準化**してから解き、正則化の強さ α は学習フレームの後ろ 1 割で選ぶ
   （2026-11-19 から。それまでは標準化なし・α = 1。1111 の 20 ブロック分割で 0.1 s 先の位相の RMSE 3.15 → 3.07°、0.2 s 先 4.34 → 4.01°。
   選ばれる α は 100〜1000）。入力を chest 相対の座標や ExtraTrees の特徴量に変える案も比べたが、標準化すれば差はわずかで、
   姿勢を予測できる（3D 表示に重ねられる）座標のままにした
2. 予測した姿勢から片側 6 特徴量（肘角度・肩角度・肘と前腕の胸基準の高さと水平距離）を作り、左右それぞれの **ExtraTrees** で h 秒先のインピーダンスを推定する
3. 左右のインピーダンスから、搬送波が消える位相差を出す: 加算点で `V1/Z_A + V2/Z_B = 0` なので **実測の W2−W1 = 180° + arg Z_B − arg Z_A**。
   AWG の指定値にするため `PHASE_OFFSET_DEG`（−4.51°）を足す（左右が同じ Z なら 175.49°）

**位相は初期位相からの相対で動かす。** 画面で位相を合わせてから「位相の自動調整」を入れると、その位相を初期位相、
そのときの推定を基準にして、以後は

    送る位相 = 初期位相 + (いまの推定から出した位相 − 基準のときの推定から出した位相)

を収録ごとに入れる（上の式の定数項や直列抵抗・回路の位相ずれの絶対値は、初期位相の中で打ち消される）。
**基準のモデルの位相は、最初の 5 回（`phase_control.REF_WARMUP`）の中央値**で、その間（約 5 秒）は位相を初期位相のまま変えない。
1 回だけで取ると、マーカーが隠れかけた回などの外れ値で記録全体がずれる（18:26 の記録で、最初の 1 回が 144°（ふだん約 172°）
だったため、腕を下ろしていても +28° ずれた位相を出し続けた）。**基準を取る 5 回は、初期位相を合わせたときと同じ姿勢でいること。**
基準を取り直すのは、記録の開始・自動調整を入れたとき・先読みを変えたとき・**手で位相を変えたとき**（それが新しい初期位相になる）。
初期位相 + 補正が 90〜270° を外れたら、その回は変えない。1118 の実測 Z では補正は中央値から −35〜+30°（5〜95 %）、最大 −55〜+46° ほど動く（1111 では −29〜+32°、最大 ±47°。1013 では ±35°、最大 ±63°）。

**Motive のラベルが左右逆のとき**は「マーカーの左右が逆」（`--swap-lr`）を入れる。モデルに渡すマーカー名だけ
R_* ↔ L_* にする（モデルは本人の左右で学習している）。記録の CSV はラベルのままなので、後で `fix_lr.py` で直す。
記録の途中で Motive が左右を入れ替えた場合（`fix_lr.py --flips` で見つかるもの）には追従しない。

**先読み h は固定**（画面の「先読み」、`--horizon`。既定 **0.1 s**、ほかに 0.15 / 0.2 s）。
収録の直前に予測するので、「最後に届いたモーションのフレーム → その収録窓 (95 ms) の中央」に合わせてある:
フレームの古さ（Motive で約 10 ms）+ 予測 約 26 ms + 位相の変更 約 16 ms（API + 待ち 5 ms）+ 窓の半分 47.5 ms ≈ 100 ms。
2026-11-18 の実機（合成モーション、古さ 4 ms）では中央値 95 ms（p10 88・p90 101）だった。

- 実際の値は `phase_pred.csv` の `t_motion` と、同じ `cap` の `ber_motion.csv` の `t_start` / `t_end` で確かめられる。
- `imp_phase_model.py` の Ridge は 0.02〜0.30 s を 0.01 s 刻みで学習してある（`phase_control.HORIZON_GRID`。0.1 / 0.2 s だけの
  古いモデルは読み込み時に断るので、`uv run train_imp_model.py` で作り直す）。
- **5 ms で位相が移り切るかは、まだ実機で確かめていない**（README の「約 5 ms で移る」による。`phase_control.PHASE_SETTLE_S`）。

（2026-11-13〜17 は、収録の後に予測して次の収録まで約 0.1 s 待っていたので、先読みを実測で約 0.14〜0.16 s に合わせる「自動」を
入れていた。収録の直前に予測するようにしたので、固定に戻した。）

画面の「直近の収録」の行に推定した Z と出した位相が出て、記録フォルダの **`phase_pred.csv`** に 1 回ごとに残る
（`cap` = **この位相で撮った収録**（`ber_motion.csv` の `cap` と同じ番号）、`t` = 予測を呼んだ時刻、`horizon` = 先読み [s]、
`phase` = 指定した値、`sent` = 位相を変えたか、`phase_model` = モデルが出した絶対の位相、`base` = 初期位相、
`ref` = 基準のモデルの位相、`warmup` = 基準を取っている回なら 1、`delta` = 補正量（`phase_model − ref`）、
`swap_lr`、`t_motion` = 先読みの起点（最後のモーションのフレームの時刻）、`t_decided` = 位相が決まった時刻、
`phase_actual`、`horizon_model` = 使った Ridge の先読み、`L_Z_R`〜`R_Z_X` [Ω]）。
**2026-11-18 より前の記録では `cap` は「予測した直前の収録」**（位相が効いたのは `cap + 1`）。

**学習データを替えるときはブランチを分ける:** 採用した学習データごとに `imp-model/<データセット名>` のブランチで
コミットする（`imp-model/1013ver1`、`imp-model/1111`、`imp-model/1118`、`imp-model/1121`、`imp-model/1125`）。新しい収録で学習し直すときは、そのブランチから

上の表、テストで使う CSV を替える。

**確かめていないこと（実機で合わせる）:**

- コイルから加算点までの直列抵抗。`SERIES_OHM`（既定 0）。抵抗があると位相の動きが小さくなる
- 振幅比 |Z_B|/|Z_A| もずれるが、直すのは位相だけ（振幅比は画面の値のまま）
- 学習データ（1125、身体に着けた VNA 計測）の Z が、BER の台に繋いだときのコイルの Z と同じとは限らない

位相の**指定値と実測には +3.9° のずれ**がある（175.53° 指定で実測 180.04°）。モデルが実測の位相を出すなら
`phase_control.PHASE_OFFSET_DEG` を足して指定値に直す。
